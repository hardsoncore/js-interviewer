
<h3>Зачем нужен Event Loop</h3>
<p><span class="accent">Event Loop (цикл событий)</span> — бесконечный цикл-диспетчер, который решает, какой кусок кода отправить в единственный поток JS следующим. Сам JavaScript однопоточный: пока в Call Stack есть хоть одна функция, ничего другого выполниться не может. Долгие операции (таймеры, сеть, события) движок отдаёт наружу — в Web APIs среды, а Event Loop возвращает их колбэки обратно, когда стек освободится.</p>

<p class="info"><strong>Главная мысль:</strong> асинхронность в JS — это не параллельность, а очерёдность. Никакой колбэк не может прервать выполняющийся код: он ждёт, пока стек станет пустым.</p>

<h3>Участники</h3>
<ul>
  <li><strong>Call Stack</strong> — то, что выполняется прямо сейчас, работает по принципу LIFO. Пока он не пуст, цикл стоит.</li>
  <li><strong>Web APIs</strong> — фоновые инструменты среды (таймеры, <code>fetch</code>, DOM-события). Отработав, они кладут колбэк в очередь и забывают о нём — очередей внутри себя они не хранят.</li>
  <li><strong>Microtask Queue</strong> — колбэки промисов (<code>.then</code>, <code>.catch</code>, <code>.finally</code>), продолжения после <code>await</code>, <code>queueMicrotask</code>. Приоритет выше, чем у макротасков.</li>
  <li><strong>Macrotask Queue</strong> — колбэки <code>setTimeout</code> и <code>setInterval</code>, события UI (клики, скролл), I/O.</li>
</ul>

<h3>Алгоритм одного тика</h3>
<ol>
  <li>Выполнить синхронный код, пока Call Stack не опустеет.</li>
  <li>Выполнить <strong>ВСЕ</strong> микротаски подряд — включая те, что добавились прямо по ходу этого шага.</li>
  <li>При необходимости отрисовать кадр (Style → Layout → Paint, обычно ~60 раз в секунду).</li>
  <li>Взять из макро-очереди <strong>ОДИН</strong> таск и выполнить его.</li>
  <li>Повторить с шага 1.</li>
</ol>

<p class="info info--blue"><strong>Формула для собеса:</strong> весь синхронный код → ВСЕ микротаски → рендер → ОДИН макротаск → повтор.</p>

<h3>Классическая задача на порядок вывода</h3>
<code class="code">
  console.log('1');
  setTimeout(() =&gt; console.log('2'), 0);
  Promise.resolve().then(() =&gt; console.log('3'));
  console.log('4');

  // 1, 4, 3, 2
</code>
<p><code>setTimeout(fn, 0)</code> не значит «выполнить сразу»: колбэк уходит в макро-очередь и ждёт, пока опустеет стек и целиком разгребётся микро-очередь.</p>

<p class="info info--orange">Микротаски, бесконечно порождающие сами себя (в <code>.then</code> снова резолвится промис), полностью замораживают страницу: рендер и макротаски не получат управления никогда, потому что очередь микротасков обязана опустеть до конца.</p>

<h3>Heap и почему стек «дешёвый»</h3>
<p><strong>Heap (куча)</strong> — большая неструктурированная область памяти для ссылочных типов (объекты, массивы, функции). В Call Stack лежат только контексты выполнения и примитивы, поэтому стек компактный, быстрый и имеет фиксированный размер — при слишком глубокой рекурсии получаем <code>RangeError: Maximum call stack size exceeded</code>.</p>

<h3>Чего нет в спецификации</h3>
<p>Термина «макротаск» в стандарте HTML нет — там есть <strong>task queues</strong> и <strong>task sources</strong> (таймеры, DOM-события, сеть, история и т. д.). Очередей на самом деле несколько, и браузер сам решает, из какого источника взять следующий таск, — поэтому два <code>setTimeout</code> и клик не обязаны исполняться в порядке добавления. Микроочередь же ровно одна и разгребается строго FIFO.</p>

<p class="info info--blue">Промисы — часть языка (ECMAScript), а не Web API. Поэтому микрозадачи ставит в очередь сам движок JS, а браузер лишь «сливает» её (microtask checkpoint) между задачами. По этой же причине микротаски работают одинаково и в браузере, и в Node.js.</p>

<h3>Где именно происходит рендеринг</h3>
<p>Шаг «отрисовать кадр» привязан не к каждому макротаску, а к vsync монитора. Порядок внутри кадра такой:</p>
<ol>
  <li>колбэки <code>requestAnimationFrame</code>;</li>
  <li>пересчёт стилей и Layout;</li>
  <li>Paint и Composite.</li>
</ol>
<p>Отсюда практическое правило: <code>rAF</code> — единственное место, где безопасно менять DOM для анимации, потому что изменения попадут ровно в ближайший кадр и не вызовут лишнего reflow. А <code>requestIdleCallback</code>, наоборот, выполняется в остаток времени кадра и подходит для некритичной фоновой работы.</p>

<h3>Нюансы таймеров</h3>
<ul>
  <li>Задержка в <code>setTimeout</code> — это <strong>минимальная</strong> гарантия, а не точное время: если стек занят, колбэк опоздает.</li>
  <li>Спецификация требует clamping: начиная с пятого уровня вложенности таймеров минимальная задержка становится 4 мс.</li>
  <li>В неактивной вкладке браузеры дросселируют таймеры до 1000 мс и более, чтобы экономить батарею.</li>
</ul>

<h3>async/await под капотом</h3>
<p>Код до первого <code>await</code> выполняется <strong>синхронно</strong>. Сам <code>await</code> — синтаксический сахар над <code>.then</code>: он ставит остаток функции в микро-очередь и возвращает управление наружу.</p>
<code class="code">
  async function f() {
    console.log('A');       // синхронно
    await null;             // точка выхода → остаток в микротаск
    console.log('B');
  }

  f();
  Promise.resolve().then(() =&gt; console.log('C'));
  console.log('D');

  // A, D, B, C
</code>
<p><code>await null</code> тоже создаёт микротаск: значение оборачивается в уже resolved-промис. Отсюда типичный антипаттерн — <code>await</code> внутри цикла: каждая итерация стоит минимум один проход по микроочереди, вместо этого собирайте промисы и отдавайте их в <code>Promise.all</code>.</p>

<h3>Другие источники микротасков</h3>
<ul>
  <li><code>queueMicrotask(fn)</code> — явно поставить микротаск без создания промиса (дешевле и не глотает исключения в цепочку).</li>
  <li><code>MutationObserver</code> — колбэки на изменение DOM доставляются как микротаски.</li>
  <li><code>IntersectionObserver</code>, напротив, работает как отдельный шаг рендер-фазы.</li>
</ul>

<h3>Отличия Node.js</h3>
<p>В Node цикл событий реализует libuv и он разбит на фазы: <em>timers</em> (<code>setTimeout</code>, <code>setInterval</code>) → <em>pending callbacks</em> → <em>poll</em> (I/O) → <em>check</em> (<code>setImmediate</code>) → <em>close callbacks</em>. Микроочередь сливается между фазами, а не только между тасками.</p>
<p>Дополнительно есть <code>process.nextTick</code> — отдельная очередь с приоритетом <strong>выше</strong> промисов: она разгребается перед микротасками. Порядок <code>setTimeout(fn, 0)</code> и <code>setImmediate(fn)</code> на верхнем уровне модуля недетерминирован (зависит от того, успел ли процесс стартовать за 1 мс), но внутри I/O-колбэка <code>setImmediate</code> всегда срабатывает первым.</p>

<p class="info info--orange">Не путайте Event Loop с многопоточностью. Настоящий параллелизм в браузере дают только <strong>Web Workers</strong> — у каждого свой поток, свой стек и свой отдельный event loop, а обмен идёт сообщениями через <code>postMessage</code>.</p>
