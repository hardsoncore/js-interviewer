
<h3>Что такое async/await</h3>
<p><span class="accent">async/await</span> — это синтаксический сахар над промисами, появившийся в <strong>ES2017 (ES8)</strong>. Новой механики здесь нет: под капотом те же промисы и микротаски. Смысл — в читаемости: асинхронный код пишется как синхронный, линейно, сверху вниз.</p>

<p class="info"><strong>Главная мысль:</strong> <code>await</code> не блокирует поток. Он приостанавливает только свою async-функцию, а движок в это время выполняет другой код; когда промис завершится, функция продолжится с того же места.</p>

<h3>Какую проблему решают</h3>
<p>Промисы избавили от Callback Hell, но длинные цепочки <code>.then()</code> породили свой шум: у каждого шага своя область видимости, и чтобы передать значение из первого шага в третий, приходится городить вложенность или внешние переменные. Условия и циклы посреди цепочки выглядят ещё тяжелее.</p>
<p>С async/await результат просто кладётся в константу, а дальше работают привычные <code>if</code>, циклы и <code>try/catch</code>.</p>

<h3>Как работают два слова</h3>
<ul>
  <li><strong>async</strong> перед функцией гарантирует одно: она всегда вернёт промис. Даже <code>return 1</code> неявно обернётся в <code>Promise.resolve(1)</code>, а брошенная ошибка станет rejected-промисом.</li>
  <li><strong>await</strong> приостанавливает функцию, пока промис справа не завершится, и возвращает его результат. Если промис отклонён — <code>await</code> бросает эту ошибку как обычное исключение.</li>
</ul>

<p class="info info--blue">Формула: <strong>async</strong> — наружу всегда промис, <strong>await</strong> — внутрь распакованное значение. Использовать <code>await</code> можно только внутри async-функции (и на верхнем уровне ES-модуля).</p>

<code class="code">
  async function getUser() {
    try {
      const response = await fetch('/api/user');
      const user = await response.json();
      return user;                      // снаружи это Promise.resolve(user)
    } catch (error) {
      console.error('Ошибка:', error);  // ловит reject любого await выше
    } finally {
      hideSpinner();                    // выполнится в любом случае
    }
  }
</code>

<h3>Обработка ошибок: try...catch...finally</h3>
<p>Reject промиса превращается в исключение, поэтому вместо <code>.catch()</code> на каждом шаге достаточно одного <code>try/catch</code> вокруг нескольких <code>await</code>. Блок <code>finally</code> — место для кода «в любом случае»: скрыть спиннер, освободить ресурсы.</p>

<h3>Главная ловушка: случайная последовательность</h3>
<p class="info info--orange">Каждый <code>await</code> ждёт завершения предыдущего. Два независимых запроса, написанных через <code>await</code> подряд, выполнятся последовательно и займут суммарное время. Независимые операции запускайте параллельно: <code>const [a, b] = await Promise.all([getA(), getB()])</code>.</p>

<p class="deep-dive">Углубленный конспект</p>

<h3>Под капотом: пауза — это микротаска</h3>
<p>Физически никакой «паузы» нет. Встречая <code>await</code>, движок разрезает функцию: всё, что идёт после, упаковывается в продолжение (continuation) и подписывается на промис — по сути это скрытый <code>.then()</code>. Сама функция немедленно возвращает управление, а продолжение попадёт в очередь микротасков, когда промис завершится. Поэтому задачки на порядок вывода с <code>await</code> решаются по тем же правилам Event Loop, что и с <code>.then()</code>.</p>
<code class="code">
  async function f() {
    console.log('2');
    await null;        // даже await не-промиса уходит в микротаски
    console.log('4');
  }

  console.log('1');
  f();                 // до первого await выполняется синхронно
  console.log('3');
  // 1, 2, 3, 4
</code>
<p>Концептуально async-функция — это машина состояний поверх генератора: до ES2017 тот же паттерн собирали вручную из генераторов и библиотеки co, а Babel до сих пор так транспилирует async/await для старых окружений.</p>

<h3>await чего угодно: thenable</h3>
<p><code>await</code> принимает любое значение. Не-промис оборачивается в <code>Promise.resolve()</code>, а объект с методом <code>.then()</code> (<strong>thenable</strong>) дожидается как настоящий промис — за счёт этого <code>await</code> совместим со старыми промис-библиотеками вроде Bluebird или jQuery Deferred.</p>

<h3>Забытый await — «висящий» промис</h3>
<p>Вызов async-функции без <code>await</code> и без <code>.catch()</code> не приостанавливает выполнение, а её reject становится unhandled rejection: внешний <code>try/catch</code> его не поймает, а в Node.js процесс завершится с ошибкой. Такие «floating promises» ловят линтером — правило <code>no-floating-promises</code> в typescript-eslint.</p>

<h3>return await: когда он не лишний</h3>
<p>Вне <code>try</code> разницы почти нет: <code>return promise</code> и <code>return await promise</code> дают один результат. Но внутри <code>try</code> разница принципиальна: <code>return promise</code> выходит из функции сразу, и reject этого промиса уже не попадёт в её <code>catch</code>; <code>return await</code> дождётся результата и поймает ошибку на месте.</p>

<h3>Top-level await и Node.js</h3>
<p><code>await</code> на верхнем уровне модуля — без обёртки в async-функцию — стандартизирован в ES2022 и работает только в ES-модулях; в CommonJS это синтаксическая ошибка. В Node.js сам async/await появился в 7.0 за флагом <code>--harmony-async-await</code> и включён по умолчанию с 7.6 (2017), а top-level await доступен без флагов с 14.8. Нюанс: модуль с top-level await задерживает выполнение всех модулей, которые его импортируют.</p>

<h3>Асинхронные циклы: for await...of</h3>
<p>Для перебора асинхронных источников — потоков, пагинированных API — есть <code>for await...of</code> (ES2018), работающий через <code>Symbol.asyncIterator</code>. И обычный цикл с <code>await</code> внутри, и <code>for await...of</code> обрабатывают элементы строго последовательно: для rate limit это то, что нужно, а для независимых элементов — та самая ловушка производительности из ядра.</p>
