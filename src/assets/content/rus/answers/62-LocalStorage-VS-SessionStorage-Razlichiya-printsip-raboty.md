<h3>Общий принцип: Web Storage API</h3>
<p><span class="accent">localStorage</span> и <span class="accent">sessionStorage</span> — два хранилища из Web Storage API с полностью одинаковым интерфейсом: синхронное хранилище строк «ключ–значение», привязанное к origin.</p>

<p class="info"><strong>Главная мысль:</strong> API у них идентичный, различие ровно одно — жизненный цикл. <strong>localStorage</strong> живёт бессрочно и общий для всех вкладок одного origin; <strong>sessionStorage</strong> живёт в пределах одной вкладки и умирает при её закрытии.</p>

<p>Общая механика:</p>
<ul>
  <li>Хранят только строки: объект перед записью сериализуем через <code>JSON.stringify()</code>, при чтении — <code>JSON.parse()</code>.</li>
  <li>API синхронный: запись больших объёмов блокирует главный поток.</li>
  <li>Данные привязаны к origin (протокол + домен + порт): <code>https://example.com</code> не видит сторадж <code>http://example.com</code> или поддомена.</li>
  <li>Лимит — около 5 МБ на origin.</li>
</ul>

<h3>API: одинаковый CRUD</h3>
<code class="code">
  localStorage.setItem('theme', 'dark');   // запись
  localStorage.getItem('theme');           // чтение → 'dark' (нет ключа → null)
  localStorage.removeItem('theme');        // удаление
  sessionStorage.clear();                  // полная очистка
</code>

<h3>Различия: время жизни и область видимости</h3>
<ul>
  <li><strong>localStorage</strong> переживает закрытие браузера, удаляется только вручную, кодом или при очистке данных сайта. Виден всем вкладкам origin; изменение в одной вкладке ловится в других через событие <code>storage</code>.</li>
  <li><strong>sessionStorage</strong> живёт, пока открыта вкладка: переживает перезагрузку страницы (F5), но не закрытие вкладки. Каждая вкладка — своё изолированное хранилище.</li>
</ul>

<h3>Когда использовать</h3>
<ul>
  <li><strong>localStorage</strong> — то, что должно пережить сессию: тема оформления, язык, пользовательские настройки, кэш некритичных данных.</li>
  <li><strong>sessionStorage</strong> — состояние одной вкладки: черновик формы, текущий шаг мастера, фильтры — чтобы две открытые вкладки не мешали друг другу.</li>
</ul>

<h3>Безопасность</h3>
<p class="info info--orange">Web Storage полностью доступен любому JS на странице — при XSS-уязвимости данные утекут. Не храни там пароли и чувствительные данные; токены аутентификации безопаснее держать в HttpOnly cookies, которые скрипту вообще недоступны.</p>

<h3>Альтернативы</h3>
<ul>
  <li><strong>Cookies</strong> — около 4 КБ, автоматически отправляются на сервер с каждым HTTP-запросом; выбираем их, когда данные должен видеть сервер.</li>
  <li><strong>IndexedDB</strong> — асинхронная база данных в браузере для больших объёмов и сложных структур; не блокирует поток и доступна в Web Workers.</li>
</ul>

<p class="deep-dive">Углубленный конспект</p>

<h3>Событие storage: синхронизация вкладок</h3>
<p>Когда одна вкладка меняет localStorage, во всех <strong>других</strong> вкладках того же origin срабатывает событие <code>storage</code> (в самой пишущей вкладке — нет). В объекте события есть <code>key</code>, <code>oldValue</code>, <code>newValue</code> и <code>url</code>. Классическое применение — logout сразу во всех вкладках:</p>
<code class="code">
  window.addEventListener('storage', (e) => {
    if (e.key === 'authToken' &amp;&amp; e.newValue === null) {
      redirectToLogin(); // токен удалили в другой вкладке
    }
  });
</code>

<h3>Тонкости жизни sessionStorage</h3>
<ul>
  <li>Переживает не только F5, но и восстановление вкладки после падения браузера (session restore).</li>
  <li>«Дублировать вкладку» копирует снапшот sessionStorage в новую вкладку — дальше хранилища живут независимо.</li>
  <li>Открытие ссылки в новой вкладке (<code>target="_blank"</code>, <code>window.open</code>) создаёт новую сессию с пустым sessionStorage.</li>
</ul>

<h3>Под капотом: где лежат данные</h3>
<p>localStorage браузер пишет на диск (в Chromium — база LevelDB в профиле пользователя), поэтому данные и переживают перезапуск. sessionStorage держится в памяти и лишь при необходимости сбрасывается на диск ради session restore. Синхронный API возможен без постоянного дискового I/O потому, что браузер держит копию стораджа в памяти рендерера: первое обращение подгружает данные origin целиком, а запись на диск идёт асинхронно в фоне.</p>

<h3>Ограничения и ловушки</h3>
<ul>
  <li>При переполнении квоты <code>setItem</code> бросает <code>QuotaExceededError</code> — запись стоит оборачивать в <code>try/catch</code>. Исторический пример: Safari в приватном режиме давал квоту 0 и кидал ошибку на любой записи.</li>
  <li>Web Storage <strong>недоступен в Web Workers и Service Workers</strong> — там только IndexedDB и Cache API.</li>
  <li><code>getItem</code> несуществующего ключа возвращает <code>null</code>; а вот если в хранилище попала строка <code>"undefined"</code> — <code>JSON.parse</code> упадёт на ней с ошибкой.</li>
  <li>Доступ как к свойству (<code>localStorage.theme = 'dark'</code>) работает, но опасен: ключ может затенить методы интерфейса (например, <code>length</code> или <code>setItem</code>). Используй методы.</li>
  <li>В режиме инкогнито оба хранилища работают, но данные живут только до закрытия приватного окна.</li>
</ul>

<h3>Сравнение с cookies и IndexedDB подробнее</h3>
<ul>
  <li><strong>Cookies</strong> — единственное хранилище, которое сервер может создать сам (заголовок <code>Set-Cookie</code>) и которое автоматически ездит в каждом HTTP-запросе; отсюда и жёсткий лимит ~4 КБ. С флагом <code>HttpOnly</code> cookie недоступна JS — поэтому она безопаснее для сессионных токенов.</li>
  <li><strong>IndexedDB</strong> — транзакционная объектная БД с индексами: хранит не только строки, но и объекты, Blob, File; квота — сотни мегабайт и больше (доля свободного диска, проверяется через <code>navigator.storage.estimate()</code>). Цена — многословный асинхронный API, поэтому на практике её берут через обёртки вроде idb или Dexie.</li>
</ul>
