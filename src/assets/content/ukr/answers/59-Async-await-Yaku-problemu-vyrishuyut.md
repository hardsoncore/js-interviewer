
<h3>Що таке async/await</h3>
<p><span class="accent">async/await</span> — це синтаксичний цукор над промісами, що з'явився в <strong>ES2017 (ES8)</strong>. Нової механіки тут немає: під капотом ті самі проміси й мікротаски. Сенс — у читабельності: асинхронний код пишеться як синхронний, лінійно, згори вниз.</p>

<p class="info"><strong>Головна думка:</strong> <code>await</code> не блокує потік. Він призупиняє лише свою async-функцію, а рушій у цей час виконує інший код; коли проміс завершиться, функція продовжиться з того самого місця.</p>

<h3>Яку проблему вирішують</h3>
<p>Проміси позбавили від Callback Hell, але довгі ланцюжки <code>.then()</code> породили свій шум: у кожного кроку своя область видимості, і щоб передати значення з першого кроку в третій, доводиться городити вкладеність або зовнішні змінні. Умови й цикли посеред ланцюжка виглядають ще важче.</p>
<p>З async/await результат просто кладеться в константу, а далі працюють звичні <code>if</code>, цикли та <code>try/catch</code>.</p>

<h3>Як працюють ці два слова</h3>
<ul>
  <li><strong>async</strong> перед функцією гарантує одне: вона завжди поверне проміс. Навіть <code>return 1</code> неявно обгорнеться в <code>Promise.resolve(1)</code>, а кинута помилка стане rejected-промісом.</li>
  <li><strong>await</strong> призупиняє функцію, доки проміс праворуч не завершиться, і повертає його результат. Якщо проміс відхилено — <code>await</code> кидає цю помилку як звичайний виняток.</li>
</ul>

<p class="info info--blue">Формула: <strong>async</strong> — назовні завжди проміс, <strong>await</strong> — всередину розпаковане значення. Використовувати <code>await</code> можна лише всередині async-функції (і на верхньому рівні ES-модуля).</p>

<code class="code">
  async function getUser() {
    try {
      const response = await fetch('/api/user');
      const user = await response.json();
      return user;                      // ззовні це Promise.resolve(user)
    } catch (error) {
      console.error('Помилка:', error); // ловить reject будь-якого await вище
    } finally {
      hideSpinner();                    // виконається в будь-якому разі
    }
  }
</code>

<h3>Обробка помилок: try...catch...finally</h3>
<p>Reject проміса перетворюється на виняток, тому замість <code>.catch()</code> на кожному кроці достатньо одного <code>try/catch</code> навколо кількох <code>await</code>. Блок <code>finally</code> — місце для коду «в будь-якому разі»: сховати спінер, звільнити ресурси.</p>

<h3>Головна пастка: випадкова послідовність</h3>
<p class="info info--orange">Кожен <code>await</code> чекає завершення попереднього. Два незалежні запити, написані через <code>await</code> поспіль, виконаються послідовно й займуть сумарний час. Незалежні операції запускайте паралельно: <code>const [a, b] = await Promise.all([getA(), getB()])</code>.</p>

<h3>Під капотом: пауза — це мікротаска</h3>
<p>Фізично жодної «паузи» немає. Зустрічаючи <code>await</code>, рушій розрізає функцію: все, що йде після, пакується в продовження (continuation) і підписується на проміс — по суті це прихований <code>.then()</code>. Сама функція негайно повертає керування, а продовження потрапить у чергу мікротасків, коли проміс завершиться. Тому задачки на порядок виводу з <code>await</code> розв'язуються за тими самими правилами Event Loop, що й з <code>.then()</code>.</p>
<code class="code">
  async function f() {
    console.log('2');
    await null;        // навіть await не-проміса йде в мікротаски
    console.log('4');
  }

  console.log('1');
  f();                 // до першого await виконується синхронно
  console.log('3');
  // 1, 2, 3, 4
</code>
<p>Концептуально async-функція — це машина станів поверх генератора: до ES2017 той самий патерн збирали вручну з генераторів і бібліотеки co, а Babel досі так транспілює async/await для старих оточень.</p>

<h3>await будь-чого: thenable</h3>
<p><code>await</code> приймає будь-яке значення. Не-проміс обгортається в <code>Promise.resolve()</code>, а об'єкт із методом <code>.then()</code> (<strong>thenable</strong>) дочікується як справжній проміс — завдяки цьому <code>await</code> сумісний зі старими проміс-бібліотеками на кшталт Bluebird чи jQuery Deferred.</p>

<h3>Забутий await — «завислий» проміс</h3>
<p>Виклик async-функції без <code>await</code> і без <code>.catch()</code> не призупиняє виконання, а її reject стає unhandled rejection: зовнішній <code>try/catch</code> його не спіймає, а в Node.js процес завершиться з помилкою. Такі «floating promises» ловлять лінтером — правило <code>no-floating-promises</code> у typescript-eslint.</p>

<h3>return await: коли він не зайвий</h3>
<p>Поза <code>try</code> різниці майже немає: <code>return promise</code> і <code>return await promise</code> дають той самий результат. Але всередині <code>try</code> різниця принципова: <code>return promise</code> виходить із функції одразу, і reject цього проміса вже не потрапить у її <code>catch</code>; <code>return await</code> дочекається результату й спіймає помилку на місці.</p>

<h3>Top-level await і Node.js</h3>
<p><code>await</code> на верхньому рівні модуля — без обгортки в async-функцію — стандартизований в ES2022 і працює лише в ES-модулях; у CommonJS це синтаксична помилка. У Node.js сам async/await з'явився в 7.0 за прапорцем <code>--harmony-async-await</code> і ввімкнений за замовчуванням з 7.6 (2017), а top-level await доступний без прапорців з 14.8. Нюанс: модуль із top-level await затримує виконання всіх модулів, які його імпортують.</p>

<h3>Асинхронні цикли: for await...of</h3>
<p>Для перебору асинхронних джерел — потоків, пагінованих API — є <code>for await...of</code> (ES2018), що працює через <code>Symbol.asyncIterator</code>. І звичайний цикл з <code>await</code> усередині, і <code>for await...of</code> обробляють елементи строго послідовно: для rate limit це те, що треба, а для незалежних елементів — та сама пастка продуктивності з ядра.</p>
