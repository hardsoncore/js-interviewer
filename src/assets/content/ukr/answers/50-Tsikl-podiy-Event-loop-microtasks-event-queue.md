
<h3>Навіщо потрібен Event Loop</h3>
<p><span class="accent">Event Loop (цикл подій)</span> — нескінченний цикл-диспетчер, який вирішує, який шматок коду відправити в єдиний потік JS наступним. Сам JavaScript однопотоковий: доки в Call Stack є хоча б одна функція, нічого іншого виконатися не може. Довгі операції (таймери, мережа, події) рушій віддає назовні — у Web APIs середовища, а Event Loop повертає їхні колбеки назад, коли стек звільниться.</p>

<p class="info"><strong>Головна думка:</strong> асинхронність у JS — це не паралельність, а черговість. Жоден колбек не може перервати код, що виконується: він чекає, доки стек стане порожнім.</p>

<h3>Учасники</h3>
<ul>
  <li><strong>Call Stack</strong> — те, що виконується прямо зараз, працює за принципом LIFO. Доки він не порожній, цикл стоїть.</li>
  <li><strong>Web APIs</strong> — фонові інструменти середовища (таймери, <code>fetch</code>, DOM-події). Відпрацювавши, вони кладуть колбек у чергу й забувають про нього — черг усередині себе вони не зберігають.</li>
  <li><strong>Microtask Queue</strong> — колбеки промісів (<code>.then</code>, <code>.catch</code>, <code>.finally</code>), продовження після <code>await</code>, <code>queueMicrotask</code>. Пріоритет вищий, ніж у макротасків.</li>
  <li><strong>Macrotask Queue</strong> — колбеки <code>setTimeout</code> і <code>setInterval</code>, події UI (кліки, скрол), I/O.</li>
</ul>

<h3>Алгоритм одного тіку</h3>
<ol>
  <li>Виконати синхронний код, доки Call Stack не спорожніє.</li>
  <li>Виконати <strong>ВСІ</strong> мікротаски поспіль — включно з тими, що додалися прямо під час цього кроку.</li>
  <li>За потреби відмалювати кадр (Style → Layout → Paint, зазвичай ~60 разів на секунду).</li>
  <li>Взяти з макрочерги <strong>ОДИН</strong> таск і виконати його.</li>
  <li>Повторити з кроку 1.</li>
</ol>

<p class="info info--blue"><strong>Формула для співбесіди:</strong> увесь синхронний код → ВСІ мікротаски → рендер → ОДИН макротаск → повтор.</p>

<h3>Класична задача на порядок виводу</h3>
<code class="code">
  console.log('1');
  setTimeout(() =&gt; console.log('2'), 0);
  Promise.resolve().then(() =&gt; console.log('3'));
  console.log('4');

  // 1, 4, 3, 2
</code>
<p><code>setTimeout(fn, 0)</code> не означає «виконати одразу»: колбек іде в макрочергу й чекає, доки спорожніє стек і повністю розгребеться мікрочерга.</p>

<p class="info info--orange">Мікротаски, що нескінченно породжують самі себе (у <code>.then</code> знову резолвиться проміс), повністю заморожують сторінку: рендер і макротаски не отримають керування ніколи, тому що черга мікротасків зобов'язана спорожніти до кінця.</p>

<h3>Heap і чому стек «дешевий»</h3>
<p><strong>Heap (купа)</strong> — велика неструктурована область пам'яті для посилальних типів (об'єкти, масиви, функції). У Call Stack лежать лише контексти виконання та примітиви, тому стек компактний, швидкий і має фіксований розмір — за надто глибокої рекурсії отримуємо <code>RangeError: Maximum call stack size exceeded</code>.</p>

<h3>Чого немає у специфікації</h3>
<p>Терміна «макротаск» у стандарті HTML немає — там є <strong>task queues</strong> і <strong>task sources</strong> (таймери, DOM-події, мережа, історія тощо). Черг насправді кілька, і браузер сам вирішує, з якого джерела взяти наступний таск, — тому два <code>setTimeout</code> і клік не зобов'язані виконуватися в порядку додавання. Мікрочерга ж рівно одна й розгрібається строго FIFO.</p>

<p class="info info--blue">Проміси — частина мови (ECMAScript), а не Web API. Тому мікрозадачі ставить у чергу сам рушій JS, а браузер лише «зливає» її (microtask checkpoint) між задачами. З цієї ж причини мікротаски працюють однаково і в браузері, і в Node.js.</p>

<h3>Де саме відбувається рендеринг</h3>
<p>Крок «відмалювати кадр» прив'язаний не до кожного макротаска, а до vsync монітора. Порядок усередині кадру такий:</p>
<ol>
  <li>колбеки <code>requestAnimationFrame</code>;</li>
  <li>перерахунок стилів і Layout;</li>
  <li>Paint і Composite.</li>
</ol>
<p>Звідси практичне правило: <code>rAF</code> — єдине місце, де безпечно змінювати DOM для анімації, тому що зміни потраплять рівно в найближчий кадр і не спричинять зайвого reflow. А <code>requestIdleCallback</code>, навпаки, виконується в залишок часу кадру й підходить для некритичної фонової роботи.</p>

<h3>Нюанси таймерів</h3>
<ul>
  <li>Затримка в <code>setTimeout</code> — це <strong>мінімальна</strong> гарантія, а не точний час: якщо стек зайнятий, колбек запізниться.</li>
  <li>Специфікація вимагає clamping: починаючи з п'ятого рівня вкладеності таймерів мінімальна затримка стає 4 мс.</li>
  <li>У неактивній вкладці браузери дроселюють таймери до 1000 мс і більше, щоб економити батарею.</li>
</ul>

<h3>async/await під капотом</h3>
<p>Код до першого <code>await</code> виконується <strong>синхронно</strong>. Сам <code>await</code> — синтаксичний цукор над <code>.then</code>: він ставить залишок функції в мікрочергу й повертає керування назовні.</p>
<code class="code">
  async function f() {
    console.log('A');       // синхронно
    await null;             // точка виходу → залишок у мікротаск
    console.log('B');
  }

  f();
  Promise.resolve().then(() =&gt; console.log('C'));
  console.log('D');

  // A, D, B, C
</code>
<p><code>await null</code> теж створює мікротаск: значення обгортається у вже resolved-проміс. Звідси типовий антипатерн — <code>await</code> усередині циклу: кожна ітерація коштує щонайменше один прохід по мікрочерзі, натомість збирайте проміси й віддавайте їх у <code>Promise.all</code>.</p>

<h3>Інші джерела мікротасків</h3>
<ul>
  <li><code>queueMicrotask(fn)</code> — явно поставити мікротаск без створення проміса (дешевше й не ковтає винятки в ланцюжок).</li>
  <li><code>MutationObserver</code> — колбеки на зміну DOM доставляються як мікротаски.</li>
  <li><code>IntersectionObserver</code>, навпаки, працює як окремий крок рендер-фази.</li>
</ul>

<h3>Відмінності Node.js</h3>
<p>У Node цикл подій реалізує libuv, і він розбитий на фази: <em>timers</em> (<code>setTimeout</code>, <code>setInterval</code>) → <em>pending callbacks</em> → <em>poll</em> (I/O) → <em>check</em> (<code>setImmediate</code>) → <em>close callbacks</em>. Мікрочерга зливається між фазами, а не тільки між тасками.</p>
<p>Додатково є <code>process.nextTick</code> — окрема черга з пріоритетом <strong>вищим</strong> за проміси: вона розгрібається перед мікротасками. Порядок <code>setTimeout(fn, 0)</code> і <code>setImmediate(fn)</code> на верхньому рівні модуля недетермінований (залежить від того, чи встиг процес стартувати за 1 мс), але всередині I/O-колбека <code>setImmediate</code> завжди спрацьовує першим.</p>

<p class="info info--orange">Не плутайте Event Loop із багатопотоковістю. Справжній паралелізм у браузері дають лише <strong>Web Workers</strong> — у кожного свій потік, свій стек і свій окремий event loop, а обмін іде повідомленнями через <code>postMessage</code>.</p>
