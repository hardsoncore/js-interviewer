
<h3>Что такое Promise</h3>
<p><span class="accent">Promise (промис)</span> — это объект-обёртка над результатом асинхронной операции, появившийся в <strong>ES6 (2015)</strong>. Он связывает «создающий» код, которому нужно время на работу, и «потребляющий», которому нужен результат: подписался через <code>.then()</code> — получишь значение, когда оно будет готово.</p>

<p class="info"><strong>Главная мысль:</strong> промис вернул управление вызывающей стороне. С колбэком мы отдаём свою функцию чужому коду и надеемся, что он вызовет её один раз и вовремя. Промис же возвращается нам как обычное значение — и подписываемся на него мы сами.</p>

<h3>Какую проблему решали</h3>
<p>До ES6 асинхронность жила только на колбэках. Одна задача — нормально, но зависимые задачи приходилось вкладывать друг в друга, и код разрастался вправо ёлкой — <strong>Callback Hell</strong>, он же <strong>Pyramid of Doom</strong>. Хуже вложенности было другое: обработка ошибок дублировалась на каждом уровне через <code>if (err)</code>, и одна забытая проверка молча съедала сбой.</p>
<p>Промисы выпрямили и то, и другое: вложенность стала плоской цепочкой, а ошибки поехали по единому каналу — один <code>.catch()</code> в конце ловит сбой любого шага.</p>

<code class="code">
  const promise = new Promise((resolve, reject) =&gt; {
    // функция-исполнитель (executor), запускается сразу
    setTimeout(() =&gt; resolve('данные'), 1000);
  });

  promise
    .then((data) =&gt; console.log(data))  // 'данные'
    .catch((err) =&gt; console.log(err));
</code>

<h3>Три состояния</h3>
<p>Промис — это конечный автомат ровно с тремя состояниями:</p>
<ul>
  <li><strong>pending</strong> — исходное: операция запущена, результата пока нет;</li>
  <li><strong>fulfilled</strong> — вызвали <code>resolve(value)</code>, работают обработчики <code>.then()</code>;</li>
  <li><strong>rejected</strong> — вызвали <code>reject(error)</code>, работает <code>.catch()</code>.</li>
</ul>

<h3>Результат замораживается навсегда</h3>
<p>Из <code>pending</code> промис уходит только один раз и становится <strong>settled</strong> (улаженным). Дальше его состояние и значение неизменны: повторные вызовы <code>resolve</code> или <code>reject</code> просто игнорируются.</p>

<p class="info info--orange">Поэтому промис — не замена событиям: событие срабатывает много раз, промис — ровно один. Зато к завершённому промису невозможно «опоздать»: подпишетесь хоть через час — <code>.then()</code> сразу отдаст сохранённый результат.</p>

<h3>then, catch, finally</h3>
<ul>
  <li><code>.then(onFulfilled, onRejected)</code> — обработчики успеха и, вторым аргументом, ошибки;</li>
  <li><code>.catch(onRejected)</code> — только ошибка; это сахар над <code>.then(null, onRejected)</code>;</li>
  <li><code>.finally(onFinally)</code> — выполнится в любом случае и без аргументов: место для «убрать спиннер», а не для разбора результата.</li>
</ul>

<p class="info info--blue">Все три метода возвращают <strong>новый</strong> промис — отсюда и растут цепочки, и способность <code>.catch()</code> перехватывать ошибку с любого предыдущего шага.</p>

<h3>Когда что выполняется</h3>
<p>Executor запускается <strong>синхронно</strong>, прямо в момент <code>new Promise</code> — промис не «ленивый», отложить его запуск нельзя. А вот колбэки <code>.then/.catch/.finally</code> всегда попадают в очередь <strong>микротасков</strong> и выполняются только после того, как опустеет стек.</p>
<code class="code">
  console.log('1');
  const p = new Promise((resolve) =&gt; {
    console.log('2');       // синхронно, внутри executor
    resolve();
  });
  p.then(() =&gt; console.log('4'));
  console.log('3');

  // 1, 2, 3, 4
</code>
<p>Отсюда практическое следствие: <code>.then()</code> вызовется асинхронно даже у уже завершённого промиса. Спецификация запрещает «иногда синхронно, иногда нет» — порядок должен быть предсказуемым всегда.</p>

<h3>Инверсия управления — главный грех колбэков</h3>
<p>Отдавая колбэк в чужую функцию, мы доверяем ей всё: вызовет ли она его вообще, вызовет ли дважды, передаст ли ошибку, вызовет ли синхронно. Промис забирает это доверие обратно в спецификацию: он гарантирует единственный вызов, асинхронность и неизменность результата. Именно поэтому промисы — не просто «красивее», а надёжнее.</p>

<h3>Что именно «заморожено»</h3>
<p>Неизменны состояние и <em>ссылка</em> на значение. Если промис зарезолвился объектом, сам объект остаётся мутабельным — <code>result.name = 'new'</code> отработает, и все подписчики увидят изменение. Гарантия промиса про идентичность значения, а не про его иммутабельность.</p>

<h3>Thenable: почему промисы совместимы со всем</h3>
<p>Промис считает «промисом» любой объект с методом <code>.then(resolve, reject)</code> — это называется <strong>thenable</strong>. Если из <code>.then()</code> вернуть такой объект, движок сам на него подпишется и дождётся. Благодаря этому нативные промисы бесшовно приняли объекты старых библиотек (Q, Bluebird, jQuery Deferred).</p>

<h3>Быстрые конструкторы и промисификация</h3>
<p><code>Promise.resolve(value)</code> и <code>Promise.reject(error)</code> создают уже завершённый промис без executor'а — удобно для заглушек в тестах, кэша и приведения значения к промису. Обратная операция — <strong>промисификация</strong>: обернуть старый API на колбэках в промис.</p>
<code class="code">
  const delay = (ms) =&gt; new Promise((resolve) =&gt; setTimeout(resolve, ms));

  const readFile = (path) =&gt; new Promise((resolve, reject) =&gt; {
    fs.readFile(path, (err, data) =&gt; err ? reject(err) : resolve(data));
  });
</code>

<h3>Необработанные отклонения</h3>
<p>Если у отклонённого промиса нет ни одного обработчика ошибки, движок сообщает об этом отдельно: в браузере — событие <code>unhandledrejection</code> на <code>window</code>, в Node.js начиная с 15-й версии процесс падает с ненулевым кодом. Ошибка в промисе не всплывает в обычный <code>try/catch</code> снаружи — только внутри <code>async/await</code>.</p>

<p class="info info--orange">Ошибка, брошенная внутри executor'а, автоматически превращается в <code>reject</code>. Но только синхронно: <code>throw</code> внутри <code>setTimeout</code> в теле executor'а промис не отклонит — он улетит в глобальный обработчик, а промис навсегда останется в <code>pending</code>.</p>

<h3>Чего у промиса нет</h3>
<ul>
  <li><strong>Отмены.</strong> Запущенную операцию промис остановить не умеет; для этого есть отдельный <code>AbortController</code>, который передают в <code>fetch</code>.</li>
  <li><strong>Прогресса.</strong> Промежуточных уведомлений нет — только финальный результат. Нужен поток значений — это уже Observable из RxJS.</li>
  <li><strong>Ленивости.</strong> Работа стартует в момент создания, а не при подписке.</li>
</ul>

<h3>Историческая справка</h3>
<p>Промисы не изобрели в ES6 — их стандартизировали. Идея пришла из языков 70–80-х (futures), а в JS вызрела в библиотеках: Q, when.js, Bluebird и общественное соглашение <strong>Promises/A+</strong>, которое и легло в основу спецификации. Отдельный урок дал jQuery Deferred: его <code>.then()</code> не соответствовал A+ (не ловил исключения и не разворачивал thenable), из-за чего цепочки вели себя иначе — jQuery привели в соответствие лишь в версии 3.</p>
