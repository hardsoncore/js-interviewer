<h3>Введение и Базовое определение</h3>
<p><span class="accent">Сервис (Service)</span> в Angular — это широкая категория сущностей, охватывающая любые значения, функции или особенности, которые нужны вашему приложению для выполнения бизнес-логики. Главная идея использования сервисов — вынесение логики, работы с данными и других вычислительных задач за пределы компонентов фронтенда.</p>
<p>Физически, сервис представляет собой TypeScript класс с узкоспециализированной задачей (например, логирование, сетевые запросы API или хранение состояния), который внедряется в любые компоненты или другие сервисы через паттерн <span class="accent">Dependency Injection (DI)</span>.</p>

<h3>Для чего нужны сервисы в Angular</h3>
<p>Основное назначение компонентов — предоставлять данные для шаблона (HTML) и реагировать на действия пользователя (клики, ввод текста). Они не должны самостоятельно получать данные с сервера, сложным образом валидировать пользовательский ввод или заниматься кэшированием.</p>
<p>Делегируя такие задачи сервисам, мы получаем ряд мощных архитектурных преимуществ:</p>
<ul>
  <li><span class="accent">Переиспользование (Reusability):</span> Один и тот же сервис (например, сервис авторизации) может быть легко использован в множестве различных компонентов без дублирования кода.</li>
  <li><span class="accent">Разделение ответственности (Separation of Concerns):</span> Компоненты становятся простыми и "глупыми", занимаясь только Presentation-логикой. Бизнес-логика живет исключительно в сервисах.</li>
  <li><span class="accent">Тестируемость (Testability):</span> Вынесенный в изолированный класс код намного легче покрывать Unit-тестами, а при тестировании компонентов мы можем просто замокать (Mock) сам сервис, чтобы протестировать реакцию UI без реальных запросов к API.</li>
</ul>

<h3>Примеры базового сервиса</h3>
<p>Давайте посмотрим на простой пример создания и внедрения сервиса для работы с пользователями.</p>
<code class="code">
  import { Injectable } from '@angular/core';

  @Injectable({
    providedIn: 'root'
  })
  export class UserService {
    private users = ['Alex', 'John', 'Alice'];

    constructor() {}

    getUsers(): string[] {
      return this.users;
    }
  }
</code>
<p>А вот паттерн использования (внедрения) этого сервиса в компоненте:</p>
<code class="code">
  import { Component } from '@angular/core';
  // Импортируем именно тип сервиса, не инициализируя его вручную!
  import { UserService } from './user.service';

  @Component({
    selector: 'app-users',
    template: '...',
  })
  export class UsersComponent {
    users: string[];

    // Внедрение зависимости происходит через constructor
    constructor(private userService: UserService) {
      this.users = this.userService.getUsers();
    }
  }
</code>

<h3>Жизненный цикл сервисов в Angular</h3>
<p>Сервисы не имеют такого богатого жизненного цикла, как директивы или компоненты (нет событий вроде <strong>ngOnInit</strong> или <strong>ngAfterViewInit</strong>). Жизненный цикл сервиса ограничивается лишь моментом его создания (вызов <strong>constructor</strong>) и уничтожения — хуком <strong>ngOnDestroy</strong>.</p>
<p>То, как долго сервис живет, зависит от того, где он был "провайднут" (подключен в дерево DI):</p>
<ul>
  <li><span class="accent">Синглтон (providedIn: 'root')</span> — сервис создается один раз при первом обращении к нему. Он живет все время работы приложения. Метод <strong>ngOnDestroy</strong> для него практически никогда не вызывается до закрытия вкладки.</li>
  <li><span class="accent">На уровне компонента (Component Providers)</span> — если сервис указан в массиве <strong>providers: [UserService]</strong> декоратора @Component, новый изолированный инстанс сервиса будет создаваться вместе с <strong>каждым</strong> новым инстансом этого компонента. И уничтожаться такой экземпляр сервиса будет тоже вместе с компонентом.</li>
  <li><span class="accent">В ленивом модуле (Lazy-loaded Module)</span> — при переходе на Lazy-модуль создается его собственный Injector, и, как следствие, будет создан свежий инстанс сервиса, специфичный только для этого модуля и его компонентов.</li>
</ul>

<h3>Важные нюансы и рекомендации</h3>
<p class="info info--orange">Избегайте прямого манипулирования DOM-деревом (через <code>document.getElementById</code>, <code>ElementRef</code> и т.д.) внутри сервисов! Сервисы предназначены для работы с абстрактными данными. Если вам нужно манипулировать DOM, выносите это в Директивы (Directives) или сами Компоненты.</p>
<p class="info info--blue">Не создавайте инстансы сервисов вручную через <code>new UserService()</code>. Это нарушает концепцию Inversion of Control и делает код нетестируемым, так как сервис перестает отслеживаться Angular DI-деревом.</p>

<p class="deep-dive">Углубленный конспект</p>
<h3>DI-деревья и утечки памяти (Memory Leaks)</h3>
<p>Очень частая и опасная ошибка связана с отписками (Unsubscribe) от <strong>RxJS Observables</strong> внутри компонентных сервисов. Если сервис является <code>'root'</code> синглтоном, созданные им долгоживущие подписки ничем не вредят.</p>
<p>Но если вы провайдите сервис <span class="accent">на уровне компонента</span>, и этот компонент часто создается/уничтожается в ходе роутинга (например, модальное окно), и при этом этот локальный сервис слушает глобальные события (например, Router events, state из NgRx store или WebSocket), то отсутствие отписки (destroy) спровоцирует огромную утечку памяти.</p>

<h4>Как правильно делать отписки внутри сервисов:</h4>
<code class="code">
  import { Injectable, OnDestroy } from '@angular/core';
  import { Subject } from 'rxjs';
  import { takeUntil } from 'rxjs/operators';

  @Injectable() // Провайдится в providers:[] определенного компонента
  export class ScopedDataService implements OnDestroy {
    private destroy$ = new Subject&lt;void&gt;();

    constructor(private globalStore: Store) {
      this.globalStore.select('user')
        .pipe(takeUntil(this.destroy$)) // автоматическая отписка по триггеру
        .subscribe(user => console.log(user));
    }

    ngOnDestroy(): void {
      // DI Angular'а уничтожит инстанс сервиса вместе с компонентом
      // и дернет этот метод для освобождения памяти
      this.destroy$.next();
      this.destroy$.complete();
    }
  }
</code>
<p>Подобный паттерн с реализацией <strong>OnDestroy</strong> в сервисе позволяет безопасно пользоваться изолированными контекстами DI, элегантно управляя памятью в связке с RxJS.</p>
