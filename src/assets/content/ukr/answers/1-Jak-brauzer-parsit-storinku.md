<h3>Critical Rendering Path</h3>
<p>Перетворення HTML, CSS і JS на інтерактивну сторінку — це <span class="accent">Critical Rendering Path (критичний шлях рендерингу)</span>: ланцюжок кроків від байтів до пікселів.</p>

<p class="info"><strong>Скелет відповіді:</strong> парсинг HTML → <code>DOM</code>, парсинг CSS → <code>CSSOM</code>, їх об'єднання в <strong>Render Tree</strong>, потім <strong>Layout → Paint → Composite</strong>. HTML парситься інкрементально, але CSS і синхронний JS цей конвеєр блокують.</p>

<h3>Парсинг HTML → DOM, CSS → CSSOM</h3>
<p>Отримавши перші байти, HTML-парсер читає код згори вниз, перетворює теги на токени, а токени — на вузли, з яких будує <span class="accent">DOM</span> — дерево вмісту сторінки. Парсинг іде інкрементально, у міру завантаження.</p>

<p>Паралельно з CSS будується <span class="accent">CSSOM</span> — дерево стилів. CSS <strong>блокує рендеринг</strong>: браузер не відмалює сторінку, доки не побудує повний CSSOM — інакше був би FOUC.</p>

<h3>JavaScript блокує парсинг</h3>
<p>За замовчуванням <code>&lt;script&gt;</code> зупиняє побудову DOM: браузер завантажує і виконує скрипт, і лише потім продовжує парсинг HTML.</p>
<ul>
  <li><code>defer</code> — завантажується у фоні, виконується після повного парсингу HTML, порядок підключення скриптів зберігається.</li>
  <li><code>async</code> — завантажується у фоні і виконується одразу по готовності, перериваючи парсинг на час виконання; порядок не гарантований.</li>
</ul>

<h3>Render Tree → Layout → Paint → Composite</h3>
<p>DOM і CSSOM об'єднуються в <span class="accent">Render Tree</span> — до нього потрапляють лише видимі вузли (немає <code>&lt;head&gt;</code>, <code>&lt;script&gt;</code>, елементів з <code>display: none</code>).</p>
<ul>
  <li><strong>Layout (Reflow)</strong> — обчислення розмірів і координат кожного елемента відносно вьюпорта.</li>
  <li><strong>Paint</strong> — заповнення пікселів: текст, кольори, межі, тіні, фони.</li>
  <li><strong>Composite</strong> — складання шарів у потрібному порядку на GPU в підсумкову картинку.</li>
</ul>

<h3>DOMContentLoaded vs load</h3>
<ul>
  <li><code>DOMContentLoaded</code> — HTML завантажено і розпарсено в DOM, без очікування стилів, картинок і фреймів.</li>
  <li><code>load</code> — сторінку завантажено повністю з усіма залежними ресурсами (картинки, стилі, фрейми).</li>
</ul>

<p class="deep-dive">Поглиблений конспект</p>

<h3>Preload Scanner</h3>
<p>Поки основний парсер стоїть на синхронному скрипті, допоміжний <span class="accent">Preload Scanner</span> «забігає» вперед по HTML, знаходить зовнішні ресурси (CSS, JS, картинки, шрифти) і починає завантажувати їх заздалегідь — так блокування одним скриптом не зупиняє все завантаження.</p>

<h3>Чому CSS парситься не інкрементально</h3>
<p>На відміну від HTML, CSSOM не можна будувати частинами: правило в кінці файлу може перевизначити правило з початку (каскад). Тому браузер чекає весь CSS, перш ніж вважати CSSOM готовим.</p>
<p class="info info--orange">Синхронний скрипт після <code>&lt;link&gt;</code> чекає побудови CSSOM: JS може читати обчислені стилі, тому не виконається, доки CSS не завантажено — так CSS здатний опосередковано заблокувати і парсинг.</p>

<h3>Що потрапляє в Render Tree</h3>
<ul>
  <li><code>display: none</code> — вузол виключається з дерева: він не рендериться взагалі.</li>
  <li><code>visibility: hidden</code> і <code>opacity: 0</code> — залишаються в дереві: елементи невидимі, але займають місце і впливають на геометрію.</li>
</ul>

<h3>Reflow і Repaint</h3>
<p><span class="accent">Reflow</span> — повторний Layout: перерахунок геометрії при зміні розмірів або позицій (ресайз вікна, вставка вузлів, читання <code>offsetHeight</code>). Дорогий, оскільки може каскадно зачепити і нащадків, і предків.</p>
<p><span class="accent">Repaint</span> — перемальовування без зміни геометрії (зміна кольору, фону). Дешевше за reflow, але все одно навантажує CPU.</p>
<p class="info info--blue">Анімація лише через <code>transform</code> і <code>opacity</code> змінює тільки етап Composite, минаючи Layout і Paint — тому йде на GPU і тримає 60 FPS (докладніше — у питанні про продуктивність анімацій).</p>

<h3>Шари і композитинг</h3>
<p>Елементи з <code>transform</code>, <code>opacity</code>, <code>will-change</code> або <code>z-index</code> можуть виноситися на окремий композитний шар. Браузер растеризує шари незалежно і склеює їх на GPU — це дозволяє рухати шар, не перемальовуючи решту сторінки.</p>
